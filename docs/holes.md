# Инвентаризация соглашений в `my_solution/` (Этап 1)

> 2026-10-17, решение = тег `baseline-handwritten` (код не менялся). «Проверено» — посчитано скриптом
> по данным выгрузки (тогда `tools/hole_evidence.py`, позже удалён вместе со старыми модулями) или запросом к данным;
> «из докстринга» — цифра из комментария тиммейта, не перепроверялась.

## Как читать

Каждое решение, зашитое в код, отнесено к одному из трёх классов.

| Класс | Что это | Что с ним делать |
|---|---|---|
| **A — дырка** | скрытое соглашение Neuron: в PDF/SCHEMA его нет, найдено по данным | выбор отдаётся движку и попадает в `rules.py` |
| **B — спецификация** | правило прямо записано в PDF или `SCHEMA.md` | остаётся в коде; движком можно только подтвердить |
| **C — каркас** | структура программы (чтение, кеши, цикл реплея), не бизнес-правило | библиотека предметной области, пишется один раз |

Колонки таблиц класса A: **дырка** — имя для `rules.py`; **где** — `файл:строки`; **сейчас** — выбор в коде;
**альтернативы** — семейство кирпичиков; **проверка** — target или диагностика, на которой варианты различаются;
**данные / сложность** — сколько строк различают варианты и насколько трудно найти выбор машиной:
● легко (один target, перебор семейства, кейс есть или почти есть) · ●● средне (нужна симуляция, но есть диагностика
по шагу) · ●●● сложно (связано с другими дырками через реплей t3/t4 или нестандартный кирпичик).
«Нет данных» — ни одна строка выгрузки не различает варианты: выбор остаётся допущением, движок оставит простейший.

Проверка по шагу (teacher forcing) возможна для двух самых трудных групп:
- **t3/t4:** `t3_booking` даёт паи каждой проводки, а заказы в `NRBOOK` полные. Значит, паи на любой день известны без
  реплея, и каждое списание проверяется отдельной строкой. Дырки `charges.*` / `risk.*` / `units.*` ищутся независимо и
  быстро (сейчас один реплей t3 — 30 с).
- **t2:** `t2_projection_year` даёт стоимость на конец каждого года. Каждый год стартует с ожидаемого значения прошлого,
  и дырки `t2.*` проверяются по годам.

## Найдено попутно (для Этапа 2)

1. **Падение всей задачи на приватных данных** (риск, а не найденная ошибка). `version(...)` возвращает `None`,
   если ни одна строка не действует на дату, и следующий `[...]` бросает исключение, которое обнуляет всю задачу:
   `commission.py:22`, `commission_rates.py:10`, `ledger_rates.py:18`, `ledger_terms.py:21`, `charges.py:20,33-34`,
   `projection_rates.py:17`, `tariff_rates.py:19`. Так же `KeyError` на `risks[pid]`, `persons[...]`, `brokers[...]`.
   На этой выгрузке такого нет: у всех 306 456 премий версия на дату денег есть (проверено). Цены всех фондов идут до
   2026-07-31, а последние деньги — июнь 2026, поэтому `market.next_trade` тоже не падает (проверено).
2. **Дубли между решением и движком:** `eras.CONVERSION` / `bricks.CONVERSION`; `dates.add_months` (с якорем) /
   `bricks.add_months` (без); `dates_easter.easter` (Гаусс) / `bricks.easter` (Meeus); праздники Тичино дважды;
   `dates_years.completed_years` / `cases/t3_penalty.completed`; `FREQUENCY` / `cases/t2_offer.FREQUENCY`.
   На Этапе 2 нужен один источник.
3. **Данные, которые задачи не используют** (кандидаты для «новой цели завтра»): налоговый модуль (NRHOLD, NRADDR,
   NRTAXR, NRTAXB), `PD_PAYDAY` (дни выплаты), канал и регион брокера, `EV_FNDID`/`EV_TOFND`/`EV_PCTG`
   (заказы взяты из NRBOOK).
4. **Безопасность движка** (код тиммейта, на Этап 3): `engine.compile_brick` выполняет код LLM через `exec`, и ограничение
   builtins — не песочница (нужна проверка AST: запрет атрибутов с `_`). `llm.py` шлёт токен по HTTP (лучше SSH-туннель).
